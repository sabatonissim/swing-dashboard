## 2. ארכיטקטורה כללית

```
[GitHub Repository: sabatonissim/swing-dashboard — PUBLIC]
         |
         ├── Vercel (Frontend)
         │     └── index.html
         │
         ├── Render (Backend API — Free Web Service)
         │     └── api_server.py — FastAPI, "נרדם" אחרי 15 דק' חוסר פעילות
         │
         ├── Neon (Postgres — Free Tier)
         │     └── מסד הנתונים — "auto-suspend" אחרי ~5 דק' חוסר פעילות ב-DB
         │
         └── GitHub Actions (מחליף את ה-Cron Jobs של Railway — חינמי ללא הגבלה, כי הריפו ציבורי)
               ├── stock-scanner.yml          — מריץ pipeline_a_scanner.py, 2 טריגרים לכל סשן (ראשי + גיבוי ~15 דק' אחריו)
               ├── news-aggregator.yml        — מריץ pipeline_b_news_aggregator.py
               ├── keep-render-awake.yml      — פינג ל-/api/health כל 13 דק' כדי ש-Render לא ירדם
               ├── cleanup-stale-signals.yml  — ידני בלבד (workflow_dispatch), מריץ cleanup_stale_signals.py
               └── earnings-refresh.yml       — (v13) ריצה קצרה (~2-3 דק') ל-heatmap + תוצאות דוחות: `python pipeline_a_scanner.py --quick`
```

**עיקרון (תוקן v13):** שינוי קוד → push ל-GitHub → **Render** מתעדכן אוטומטית; **Vercel אצל המשתמש לא מתעדכן לבד — צריך להעלות/לפרוס גם שם ידנית** (אפשרות: לחבר את פרויקט Vercel לריפו). ה-workflows של GitHub Actions רצים מתוך הריפו, בלי תלות בשרת חי — **אבל תזמון ה-`schedule` שלהם לא אמין (3–12 שעות איחור, סעיף 19.6)**; לכן המלצה: להפעיל אותם בטריגר חיצוני (`workflow_dispatch`).

### ⚠️ למה הריפו ציבורי (החלטה מכוונת, לא שגיאה)
GitHub Actions מגביל ריפו **פרטי** ל-2,000 דקות ריצה/חודש בחינם. ריפו **ציבורי** מקבל דקות **ללא הגבלה**. הסודות (`DATABASE_URL` וכו') לא נחשפים — שמורים ב-GitHub Secrets מוצפנים, בנפרד לגמרי מהקוד.

### ⚠️ תקלת CORS אמיתית שקרתה — לזכור לעתיד
פעם אחת האתר נשאר תקוע לצמיתות על "מתחבר לשרת..." **למרות** שלוגי Render הראו בקשות מצליחות (200 OK). הסיבה: הבקשות המוצלחות בלוג היו רק מפינג ה-keep-alive האוטומטי — לא מהדפדפן בפועל. הדפדפן קיבל שגיאת **CORS**, כי ה-deploy האחרון ב-Render **לא באמת עלה** (נתקע/נכשל בשקט) והשרת המשיך להריץ קוד ישן. **אבחון:** F12 → Console בדפדפן (לא רק לוגי Render!). **תיקון:** Render → Deploys → "Deploy latest commit" ידנית.

### ⚠️ קובץ workflow חייב היכן שהוא רץ, לא היכן שהוא מתוזמן
קובץ `.yml` חייב להיות בתוך `.github/workflows/`, אבל כל סקריפט Python שהוא מריץ חייב להיות **בשורש הריפו**. שגיאה `can't open file '.../cleanup_stale_signals.py'` = כמעט תמיד זה.

## 4. טכנולוגיות

### Frontend
- **Vanilla HTML/CSS/JS** — קובץ אחד, בלי framework, בלי build process
- **TradingView Widget (חינמי, `tv.js`)** — הגרפים הראשיים בכל מקום, עם ממוצע נע 150 יום אדום. **החלטה מפורשת של המשתמש: נשאר כמו שהוא.** הווידג'ט החינמי לא מאפשר לצייר עליו קווים מהקוד שלנו (זה רק ב-Charting Library המסחרי), והמשתמש בחר **לא** להחליף ל-`lightweight-charts`. במקום זה יש תרשים סכמטי נפרד משלנו (SVG) בעמוד Deep Dive — ראה סעיף 7.1
- **Chart.js 4.5.0** — פונדמנטלס, סקטורים, equity curve
- **Treemap מותאם-אישית (vanilla JS)** — מפת חום דו-שכבתית לפי סקטור GICS
- **SVG inline שנוצר ב-JS** — מד פחד/תאווה (חצי-עיגול עם מחוג), תרשים "מבנה טכני" (נרות + קווים + תאריכים)
- **(עודכן 26.10, סעיף 26.1) הפריסה תמיד שמאל-לימין (`dir="ltr"` קבוע) בשתי השפות; טקסט עברי נהפך ל-RTL אלמנט-אלמנט ע"י `hebDir`.** הסעיף הישן ("RTL עברית קבוע") בוטל.
- **localStorage** ל: שפה, פילטר קטגוריות חדשות, **`swing_token` / `swing_user` (התחברות), `swing_theme` (`dark`|`light`, ברירת מחדל `dark`)**
- **Google Identity Services** (`accounts.google.com/gsi/client`) — כפתור "התחבר עם Google" בתוך תפריט הפרופיל (v13)

- ❌ **cron-job.org / UptimeRobot / כל שירות תזמון חיצוני** — נדחה (בעבר, ושוב ב-v13 — המשתמש לא רוצה הרשמות נוספות). הפתרון: `scheduler.py` בתוך השרת (19.6). נבדקו ונפסלו גם: Vercel Cron (Hobby: פעם ביום, דיוק של שעה, ב-UTC, ותוכנית Hobby לשימוש לא-מסחרי), Google Cloud Scheduler (דורש חשבון חיוב), ריצת GitHub ארוכה שמחכה (לא שימוש ראוי ב-Actions)

## 5. מסד הנתונים (Postgres, Neon)

### ⚠️ נקודות קריטיות תפעוליות
- **Neon branches**: הנתונים החיים נמצאים ב-branch **`live`** (שמו הקודם `import-2026-08...`; הוגדר כברירת מחדל ב-18.10.2026, כך ש-SQL Editor נפתח עליו). ה-branch הישן `production` (שהוחלף לשם `old-production` אם שונה) מכיל רק 8 אירועי אנליטיקה ישנים מאוגוסט — **לא** להריץ עליו שאילתות ולא למחוק לפני בדיקה. כתובות החיבור (`DATABASE_URL`) לא השתנו בשינוי השם.
- **Neon auto-suspend**: כל קוד עם עבודה ארוכה **חייב לפתוח חיבור בסמוך לכתיבה**.

### `scanned_stocks` — תוצאות הסריקה
עמודות עיקריות: `ticker`, `trigger_text_he/en`, `pattern_type`, `swing_score`, `entry_price`, `support_level`, `resistance_targets`, `sma50/150/200`, `trend_stage`, `atr_value/pct`, `rs_rating`, `days_to_earnings`, `forward_return_10d/20d`, `breakout_volume_pct`, `change_pct`, `exchange`, `market_cap`, `avg_volume_20d`, `timestamp`.
`/api/stocks` מחזיר שורה אחת לכל טיקר (`DISTINCT ON`) + `repeat_count_14d`.
**ערכי `pattern_type` האפשריים:** `cup_handle`, `cup_no_handle`, `double_bottom`, `52w_high`, `horizontal_resistance_breakout`, `golden_cross`, `ma150_breakout`, `bull_flag`, `ascending_triangle`, `ascending_trendline`, `ma150_support_bounce`, `horizontal_level_bounce`, `macd_cross`, `momentum_surge`, `rsi_bounce`, `descending_trendline_breakout`.
**ניקוי היסטורי שבוצע:** `cleanup_stale_signals.py` מחק 10,664 מתוך 12,914 שורות (82%) חזרות ישנות.

### `macro_news` — חדשות (עודכן)
`id`, `category_tag`, `summary_he` (**הכותרת המתורגמת בלבד**, לא תקציר אמיתי), `summary_en` (הכותרת המקורית), `impact_level` (`High`/`Critical`), `source_url` (UNIQUE), `hook_he` (הסבר גנרי לקטגוריה, לא ספציפי לכתבה), **`body_en` / `body_he` (חדש)** — תקציר ה-RSS של המו"ל, מנוקה מ-HTML ומתורגם, `timestamp`.
- העמודות החדשות נוספות ע"י `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` ב-`init_db()` של `pipeline_b` — **רק בריצה הבאה של pipeline_b אחרי ה-deploy**. כתבות ישנות לא יקבלו body; רק חדשות מכאן והלאה.
- ל-`api_server.py` יש `CREATE TABLE IF NOT EXISTS macro_news` משלו **בלי** עמודות ה-body (בלתי מזיק כי כל ה-endpoints משתמשים ב-`SELECT *`; אם תהיה בעיית סכמה — להוסיף שם גם את ה-ALTER).
- פידי Google News בדרך כלל לא נותנים body אמיתי (ה-summary שם הוא רק הכותרת עטופה בקישור) — `_clean_rss_body` מחזיר ריק ואז לא מוצג "עוד מהמקור".

### `analytics_events`, `ui_strings`
- `analytics_events` (`event_type`, `entity_id`, `session_id`) — נכתב ע"י `POST /api/track` (הפרונט קורא לו דרך `track()`: חיפושי מניות, הוספה לרשימת מעקב וכו'). נקרא ע"י `/api/analytics/*`.
- `ui_strings` — טקסטי ממשק שמוגשים ע"י `/api/ui-strings`.

### `econ_events` (v11)
`event_key` (PK = `<type>-<YYYY-MM-DD>`), `etype`, `event_date`, `forecast`, `previous`, `actual`, `period` (תקופת הייחוס של הפרסום, למשל ספטמבר 2026), `updated_at`. נוצרת ע"י `econ_calendar.ensure_table()` בקריאה הראשונה (לא ב-`init_db`; העמודה `period` נוספת אוטומטית). **שני תפקידים:** (1) שומר `actual`/`forecast` שכבר פורסמו; (2) **גיבוי ללוח הזמנים** — אם אתר BLS/BEA/Census נופל, האירועים שלו נלקחים משם (רק לסוגי האירועים של המקור שנפל, כדי לא להשאיר כפילות אחרי דחיית פרסום). נכתבות רק שורות חדשות/שהשתנו.

### `universe_movers`, `earnings_calendar`, `sec_cik_cache`, `watchlist`
- `universe_movers`: heatmap + fallback "הכי זזות".
- `earnings_calendar`: `ticker`, `report_date`, `session`, `market_cap`, `eps_estimate/actual`, `surprise_pct`, `revenue_estimate/actual`, `revenue_surprise_pct`. `PRIMARY KEY (ticker, report_date)`. `revenue_estimate` נשמר עם COALESCE שמעדיף את הערך **הישן** (ה-"0q" של yfinance מתגלגל קדימה אחרי הדיווח); `eps_actual`/`revenue_actual` מעדיפים את החדש. **(v9) + `eps_source_date`, `revenue_period_end`** — התאריך של התקופה שממנה נלקח כל "actual" (מקור הערך), כדי שאפשר יהיה לוודא שהוא שייך לדיווח הנכון. ערכי actual בלי תאריך כזה (נכתבו לפני v9) מתאפסים פעם אחת ונשלפים מחדש.
- `sec_cik_cache`: מיפוי טיקר→CIK.
- `watchlist` **(v13 — אישית)**: `user_id`, `ticker`, `added_at`; אינדקס ייחודי `(user_id, ticker)` (ה-PK הישן על `ticker` בלבד נמחק ב-`init_db`). שורות ישנות (`user_id` NULL) עוברות **למשתמש הראשון שמתחבר** (הבעלים).

### `users` (v13)
`id` (SERIAL), `google_sub` (UNIQUE — מזהה גוגל קבוע), `email`, `name`, `picture`, `created_at`, `last_login`. נוצרת ב-`init_db` של `api_server.py`. נכתבת ב-`POST /api/auth/google` (upsert לפי `google_sub`).

### `ai_daily_digests` (v16) — הטבלה הנוכחית של הסיכום היומי
`day` (DATE, מפתח), `updated_at`, `item_count`, `last_item_id` (ה-id האחרון של `macro_news` שנכלל), `updates`, `since_rebuild`, `is_final`, `model`, `payload` (TEXT = JSON). שורה אחת ליום; נוצרת אוטומטית ע"י `ai_digest.py`; נמחקת אחרי 90 יום. ראה סעיף 23.

### `ai_digests` (v13.1) — ישנה, כבר לא נכתבת ולא נקראת
`id`, `generated_at`, `window_hours`, `item_count`, `model`, `payload` (TEXT = JSON). נוצרת אוטומטית (`CREATE TABLE IF NOT EXISTS`) ע"י `ai_digest.py`; שורות מעל 7 ימים נמחקות. השרת קורא את השורה האחרונה מ-36 השעות האחרונות; אם הטבלה חסרה/ריקה — `ai_summary: null` והפרונט מציג הודעה "עדיין אין סיכום".

## 7. Pipeline A — סורק מניות טכני

### לוח זמנים
`stock-scanner.yml`: 2 טריגרים לכל סשן (ראשי + גיבוי ~15 דק'). `should_skip_scan()` מונע כפילות (90 דק'). **לעדכן ידנית ליד סוף אוקטובר/מרץ** (שעון קיץ/חורף).

### Universe
S&P 500 + Nasdaq 100 + תוספות. פילטרים: מחיר > $10, נפח 20 יום > 1.5M, שווי שוק > $1.5B, NYSE/NASDAQ. `build_scan_universe()` מסובב סדר לפי יום בשנה.

### תבניות — 15 גלאים (16 ערכי `pattern_type`, כי כוס עם/בלי ידית הם גלאי אחד)
רמה 1 (מבניות, ציון גבוה): Cup & Handle, Double Bottom, 52w high, פריצת התנגדות אופקית, Golden Cross, פריצת ממוצע 150, Bull Flag, משולש עולה, קו מגמה עולה, קפיצה על ממוצע 150, קפיצה על תמיכה אופקית. רמה 2 (גנריים, ציון נמוך): MACD, Momentum Surge, RSI Bounce. + שבירת קו מגמה יורד.
**סדר העדיפויות כשכמה תבניות מתאימות למניה אחת** (שרשרת `elif` בסורק): cup_handle > double_bottom > 52w_high > cup_no_handle > horizontal_resistance_breakout > golden_cross > ma150_breakout > bull_flag > ascending_triangle > ascending_trendline > ma150_support_bounce > horizontal_level_bounce > macd_cross > momentum_surge > rsi_bounce > descending_trendline_breakout (קטגוריית "else" — הכי נמוך).
**Freshness check** לכל תבניות הפריצה (אתמול לא חצה, היום חוצה) — מונע ריבוי סימון.
**זיהוי הכוס (v10):** שפה שמאלית (שיא מקומי) → ירידה של 12–35% → התאוששות עד 5% מתחת לאותה שפה, בתוך 20–110 ימים, תחתית עגולה באמצע (לא V ולא בקצה). **קו הפריצה = השפה השמאלית** (ההתנגדות האמיתית), היעד = שפה + עומק הכוס. הסורק מסמן **רק פריצה טרייה** (הסגירה הראשונה מעל השפה עד 5 ימי מסחר אחורה, ולא יותר מ-8% מעליה). ב-Deep Dive מוצגת גם כוס שפרצה לפני עד 40 יום (מסומנת בגלוי כ"לא טרייה" ומדורגת נמוך ברשימה), או כוס שמתקרבת לשפה. ידית מזוהה (איחוד רדוד של 5–25 ימים לפני הפריצה) ומשפיעה על `cup_handle` מול `cup_no_handle` בסורק.

### יומן דוחות שבועי
40 הגדולים (לפי שווי שוק) בחלון **-6/+7 ימים** + טיקרים מוגנים שכבר דיווחו. **לקח:** `revenue_actual` מגיע מ-`quarterly_income_stmt` של yfinance באיחור של כמה ימים אחרי ה-EPS, ולכן חלון אחורי של יומיים מחק שורות לפני שההכנסות הגיעו. **לקח שני:** הרחבת החלון מגדילה את מאגר המועמדים שמתחרים על 40 המקומות, ודחקה החוצה דיווח ישן יותר — לכן ההגנה על `eps_actual IS NOT NULL`. בכל ריצה נכתב לוג כמה שורות "דיווחו" עדיין בלי `revenue_actual`.

**⚠️ באג שנמצא ב-v8 (נמצא ע"י המשתמש ואומת מול הדוחות הרשמיים — Micron, Jabil, FactSet, 30.9.2026) ותוקן ב-v9:**
- **הכנסות:** `revenue_actual` נלקח מהעמודה האחרונה ב-`quarterly_income_stmt` בלי לבדוק לאיזה רבעון היא שייכת. Yahoo מעדכן את הדוחות באיחור, ולכן נלקח **הרבעון הקודם** והוצג כאילו זה הדיווח החדש (Micron $41.46B במקום $54.23B; Jabil $8.75B במקום $10.6B; FactSet $622.9M במקום $634.7M) — וחץ ההפתעה הצביע לכיוון ההפוך בשלושתן.
- **EPS של Micron:** `_fetch_eps_result` בחר את השורה הכי קרובה בתאריך **בלי הגבלת מרחק**; כש-Yahoo עוד לא רשם את הדיווח החדש נבחרה שורת הרבעון הקודם ($25.11 מול $20.69 במקום $33.42 מול $31.16).
- **הפתעת הכנסות** חושבה מהערכה "טרייה" אחרי שהיא כבר התגלגלה לרבעון הבא.
- **התיקון:** (1) שורת EPS מתקבלת רק אם תאריכה עד 3 ימים מתאריך הדיווח; (2) הכנסות נקראות רק מעמודה שהסתיימה לכל היותר 85 יום לפני הדיווח (הרבעון הקודם תמיד רחוק יותר), אחרת נשאר ריק עד שהדוח יתעדכן בסריקה מאוחרת יותר; (3) הערכת הכנסות נשלפת רק **לפני** הדיווח ונשמרת אחריו; (4) אחוז הפתעת ההכנסות מחושב ב-SQL מהערך השמור (הערכה לפני הדיווח + actual מאומת) — אף פעם לא מערבב שני רבעונים; (5) `api_server.init_db` והסורק מנקים פעם אחת ערכי actual ישנים שאין להם מקור מאומת.
- **מגבלות:** ההערכות והחריגות הן של Yahoo (קונצנזוס שונה במעט ממקורות אחרים — Micron: Yahoo ≈ $51.1B, ממקורות אחרים ≈ $50.5B); EPS הוא ה-adjusted/non-GAAP כפי ש-Yahoo מדווח. אחרי הדיווח, בין כמה שעות לימים הכנסות יופיעו ריקות עד ש-Yahoo מעדכן — **זה מכוון** (ריק עדיף על רבעון שגוי).

### 7.1 מבנה טכני נוכחי (Deep Dive) — עותק "מועמד" של הגלאים
**איפה:** `api_server.py` (פונקציות `_setup_*`, `_compute_setup_candidates`, `_SETUP_EXPLANATIONS`, `_SETUP_PRIORITY`, `_SCANNER_PATTERN_TO_SETUP_ID`). **לא מייבא** את `pipeline_a_scanner.py` (שני שירותים נפרדים) — הלוגיקה **משוכפלת בכוונה**. ⚠️ **סיכון drift:** שינוי גלאי בסורק דורש שינוי מקביל כאן, אחרת ההתאמה בין הסריקה ל-Deep Dive תישבר (זה קרה עם IFF, ואחר כך עם KDP — ראה "התאמה מלאה לסורק" למטה).

**התאמה מלאה לסורק (v6) — `SCANNER PARITY` ב-`api_server.py`:** מדידה סינתטית (כמה אלפי סדרות מחיר) הראתה ש-4 גלאים סטו לגמרי: קו מגמה עולה (סורק: רגרסיה על 60 ימים; Deep Dive: קו בין שני שפלים על 150 יום — **94% מהסימונים של הסורק לא נמצאו**), משולש עולה (100%), שבירת קו מגמה יורד (95%) ופריצת ממוצע 150 (47%). תיקון: לכל אחד מהם יש עכשיו פונקציית `_scanner_rule_*` שהיא **העתק שורה-בשורה של חוק הסורק**, וה-`_setup_*` המתאים קורא לה **קודם**; אם הסורק היה מסמן — Deep Dive מציג את אותה תבנית באותה רמה. כך גם נסגרו פערים קטנים ב-52w high (הסורק מסמן כל סגירה מעל השיא, לא רק עד 3%), קפיצה מממוצע 150, קפיצה מרמה אופקית וצלב זהב (חלון של 3 ברים). Deep Dive מושך עכשיו `2y` (כמו הסורק) ולא `1y`. אחרי התיקון: 0 פספוסים ב-8,000 סדרות, ורמות המפתח זהות לרמות הסורק.

**קווי מגמה (v7) — איך נבחר קו:** הקו הישן היה רגרסיה ליניארית דרך *כל* השפלים ב-60 יום, ולכן עבר **באמצע** הנרות ולא מתחתיהם (בדיפ-דייב של מניה אמיתית הוא לא נגע באף שפל). עכשיו `fit_trendline()` בסורק ו-`_fit_trendline()` בשרת (**תאומות — לשנות ביחד**): קו נמתח בין **שני שפלי-פתיל אמיתיים** (תמיכה) או שיאי-פתיל (התנגדות), חוקי רק אם אף נר לא חודר אותו ביותר מ-1.5%, מרחק מינימלי 15 ברים בין העוגנים, **לפחות 3 נגיעות** (סטייה עד 1% מהקו), חיפוש עד 150 יום אחורה. בין כמה קווים חוקיים נבחר זה עם הכי הרבה נגיעות, אחר כך הארוך ביותר. קפיצה מקו תמיכה עולה דורשת גם **מגע בפועל בקו ב-3 הימים האחרונים** (לא רק קרבה). הגרף מסמן עיגול על כל נקודת נגיעה. הקבועים: `TRENDLINE_SEARCH_DAYS / TOLERANCE / TOUCH_TOL / MIN_SPAN_BARS / MIN_TOUCHES` (סורק) ו-`_TL_*` (שרת). **השפעה צפויה:** כמות איתותי קו מגמה תשתנה (בבדיקה סינתטית: עולה ~1.9x, שבירת יורד ~2.9x, כי הכלל הישן החמיץ קווים תקינים) — **לא נמדד על נתונים אמיתיים**; אם יש יותר מדי איתותים, להעלות `MIN_TOUCHES` או להקטין `TOLERANCE`. סימונים ישנים ב-DB לא משתנים.

**`scan_signal` ב-`/api/technical-setup`:** אם הסורק סימן את המניה ב-5 הימים האחרונים אבל התבנית לא מתקיימת בבדיקה החיה (המחיר זז), או שזה `macd_cross` (לא נבדק ב-Deep Dive) — השרת מחזיר `scan_signal.reproduced=false` והפרונט מציג הודעה כתומה מעל התוצאה, **במקום להציג בשקט תבנית אחרת** (זה מה שקרה ב-KDP: סורק = קו מגמה, Deep Dive = תחתית כפולה).

**באג שנמצא ותוקן בסורק:** ב-`detect_horizontal_level_bounce` הושוותה שבר (0.012) לאחוז מעוגל (1.2), ולכן נבחרה הרמה **האחרונה** שעונה על התנאי ולא **הקרובה ביותר** לשפל היום. תוקן; סימונים חדשים יציגו את הרמה הקרובה. סימונים ישנים ב-DB לא משתנים.

**כלל לעתיד:** שינוי גלאי בסורק → לשנות את ה-`_scanner_rule_*` התאום (ובקווי מגמה: את `fit_trendline` ↔ `_fit_trendline`), ולבקש מ-Claude לוודא שהסורק ו-Deep Dive עדיין מסכימים על נתונים סינתטיים.

**ההבדל מהסורק:** הסורק מסמן רק **ביום הפריצה עצמה** (בינארי). כאן כל גלאי מחזיר גם **תבנית שעדיין נבנית**: `stage` = `approaching` / `triggered` / `holding`, `key_level`, `distance_pct`, `lines[]` (קואורדינטות לשרטוט), ולפעמים `target_price`/`target_pct` (מדידת גובה קלאסית: כוס, משולש עולה, דגל שורי, תחתית כפולה).

**13 תבניות:** cup_and_handle, double_bottom, week52_high_breakout, bull_flag, ascending_triangle, golden_cross, ascending_trendline_support, descending_trendline_breakout, horizontal_resistance_breakout, horizontal_support_bounce, ma150_support (ממזג את ma150_breakout + ma150_support_bounce של הסורק), rsi_oversold_bounce, momentum_surge. **בלי MACD.** RSI ו-momentum **בלי קווים** (אין רמת מחיר) — רק טקסט.

**בחירת המועמד הראשי:** (1) פעיל (`triggered`/`holding`) קודם, לפי `_SETUP_PRIORITY` (אותו סדר יחסי כמו שרשרת ה-elif בסורק); (2) אחרת ה-`approaching` הקרוב ביותר לטריגר. (3) **`scan_match`:** אם `scanned_stocks` מכיל לטיקר איתות ב-5 הימים האחרונים והתבנית תואמת מועמד שנמצא — היא מוקפצת לראש ומסומנת `matches_scan`.

**לקחים שנלמדו (IFF):** (א) בפריצת התנגדות אופקית, הסורק בוחר את הרמה **הגבוהה ביותר שנפרצה** (סגירה ≥ רמה×1.01), לא "הקרובה ביותר למחיר" — הגרסה הראשונה שלנו בחרה לא נכון והציגה מספר אחר. (ב) קווי מגמה: **לא רגרסיה** (נראית שרירותית, לא נוגעת בפתילים) אלא חיבור בין **שתי נקודות swing אמיתיות** (ראשונה ואחרונה) + בדיקה שאף swing אחר לא שובר את הקו ביותר מ-2%. (ג) כשהרמה נפרצה — התווית: "התנגדות → הפכה לתמיכה".

**Frontend:** `renderTechnicalSetup` / `buildTechnicalSetupSvg` — נרות OHLC אמיתיים + קווים + **תאריך עוגן ליד כל קו + ציר תאריכים** (התחלה/אמצע/היום, כדי לדעת אם זה ימים או שבועות). מצייר את המועמד הראשי **ועד 2 נוספים** שפעילים או בטווח 6% ומציג אותם ברשימה מתחת. ממוקם ב-Deep Dive **אחרי שורת הסטטיסטיקות ולפני "על החברה"**. דיסקליימר בכל הסבר: ניתוח טכני היסטורי, לא המלצה.

(הסבר קצר). שעות מוצגות ב-ET וגם בשעון המקומי של הגולש. כל מבט נטען בפעם הראשונה שנפתח; רענון (5 דק') רק כשהמבט על המסך.

לכל אירוע: שם (he/en), רמת השפעה, שעת פרסום קבועה (ET), הסבר "מה זה" (he/en), רשימת "משפיע על" (ציפיות ריבית, תשואות, דולר, S&P, נאסד"ק, צמיחה/טק, בנקים, מחזוריות, צרכנים), הגדרת קריאת "בפועל" מ-FRED (series + טרנספורמציה + פורמט), ורגקסים להתאמת כותרות הצפי.
**GDP:** מוצג רק האומדן הראשון (Advance) — האומדן השני והשלישי הם עדכונים ולא נכללים (שגיאה בפעם הראשונה = לא להציג מספר ישן כ"בפועל").
**מה נמדד:** CPI/Core CPI/PCE/Core PCE/PPI/מכירות = שינוי חודשי (`m/m`); NFP = שינוי במשרות (K); GDP = רבעוני מאוּנתּן; FOMC = הגבול העליון של טווח הריבית.

### ארכיטקטורה: Data Provider → Processing → UI
```
טבלת FOMC (federalreserve.gov) ──────────┐
BLS bls.ics ─► CPI/Core/PPI/NFP/אבטלה/JOLTS ┤
BEA ics ─────► GDP / PCE / Core PCE ────────┼─► schedule ─┐
Census html ─► מכירות קמעונאיות ────────────┤             │
כללים: claims (כל חמישי) + הערכות ISM/CB/UMich ┘           ├─► _merge() ─► enrich ─► build_calendar() ─► /api/econ-calendar ─► index.html
ספק צפי מורשה (אופציונלי, plug-in) ► forecast+prev ─────────┤
FRED CSV ציבורי ► actual / previous (לפי תקופת ייחוס) ──────┤
Postgres econ_events ► ערכים שמורים + גיבוי לוח זמנים ──────┘
```
ה-UI (`renderEconCalendar` / `econCardHtml`) תלוי **רק** במבנה האחיד: `id, type, name_en/he, impact, datetime_utc, date_et, time_et, estimated, forecast, previous, actual, has_actual_source, status (upcoming|pending|released|released_no_data), surprise {direction above|below|inline, diff}, what_en/he, affects[], sources{}` + `meta.providers`. **שום מקום בפרונט לא מזכיר ספק מסוים** (למעט שורת ייחוס FRED/הפד בכותרת התחתונה). `meta.forecast_provider` קובע אם מוצגת עמודת הצפי (`none` → שתי עמודות: קודם/בפועל).

### איך הנתונים מגיעים (בקשה אחת לדפדפן)
1. הפרונט קורא `/api/econ-calendar` בטעינה ואז כל 5 דק' (+ רינדור מחדש כל דקה לספירה לאחור).
2. `_merge`: כל ספק לוח זמנים נקרא בנפרד (קאש 6 שעות, ובכשל — עותק אחרון תקין); לכל פרסום נגזרת **תקופת ייחוס** (`period`): CPI/PPI/NFP/אבטלה = החודש הקודם, JOLTS = החודש של (תאריך פרסום − 45 יום), claims = השבת שלפני, GDP/PCE/Retail = מהכותרת/הטבלה של BEA/Census. אם מחובר ספק צפי — הוא מאשר/מחליף תאריך משוער (עד 4 ימים) ונותן שעה וצפי.
3. `enrich` (במקביל, 4 threads): לאירוע שפורסם ב-3 הימים האחרונים בלי `actual` — מחפשים ב-CSV של FRED את **שורת תקופת הייחוס המדויקת**; לאירוע עתידי בלי `previous` — הערך האחרון ב-CSV.
4. הערכים נשמרים ב-`econ_events`; ערכים שמורים ממלאים חורים.

### איך Forecast / Previous / Actual מטופלים
- **Forecast:** רק מספק צפי מורשה (כשמחובר). אין ספק → העמודה מוסתרת (לא שורות של "—"). ספק קיים אך אירוע בלי צפי → "—". נשמר ב-DB כדי לא להיעלם.
- **Previous:** מהספק אם קיים; אחרת הערך האחרון מ-FRED. **אחרי פרסום** מוחלף ב-previous שמחושב מהסדרה של FRED (כולל תיקונים רטרואקטיביים).
- **Actual:** רק FRED (CSV ציבורי). **בדיקת תקופת ייחוס:** הנתון מתקבל רק אם הסדרה כבר מכילה את התקופה המדויקת של הפרסום (למשל ספטמבר 2026 ל-CPI של 14.10) — אחרת FRED עוד לא קלט את הדוח ולא מציגים את נתון החודש הקודם; סטטוס `pending` ("ממתין לנתון"), בדיקה חוזרת כל ~2.5 דק'. **שינויים באחוזים (m/m) ושינוי משרות מחושבים מקומית** מרמות המדד/התעסוקה. FOMC: הריבית נקראת מ-`DFEDTARU` ביום **שאחרי** ההחלטה.
- **Surprise:** `compute_surprise` משווה מספרית (K/M/B/% מנורמלים). מעל/מתחת/בהתאם + הפרש. **בכוונה בלי ירוק/אדום** — "מעל הצפי" ב-CPI הוא לא חדשות טובות, לכן צבעי טורקיז/ענבר ניטרליים.
- **אין מקור בפועל (ISM, Conference Board, מישיגן):** `has_actual_source=false` → "הנתון בפועל אינו זמין במקורות החינמיים שלנו".

### איך מחליפים ספק בעתיד (בלי לגעת ב-UI)
- **לחבר ספק צפי (v11.1 — חוזה מוכן):** ב-`econ_calendar.py` לכתוב פונקציה ללא ארגומנטים שמחזירה `[{type, when (tz-aware), forecast, previous, source}]`, למפות את שמות האירועים של הספק עם `match_event_type(title)` (להוסיף רגקסים ל-`CATALOG[...]["match"]`; כותרות שלא מופו נרשמות ב-`/api/econ-calendar/debug`), לפרמט מספרים כמו ה-`fmt` של האירוע ("0.3%", "175K", "7.20M"), לכבד rate limits עם קאש (`_cget/_cset`), ואז: `FORECAST_PROVIDERS["name"] = fn` + `ECON_FORECAST_PROVIDER=name` ב-Render. **זה הכול** — ה-API וה-UI לא משתנים; עמודת הצפי ושורת "מעל/מתחת לצפי" מופיעות לבד. נבדק עם ספק דמה (חיבור, כשל, ספק לא קיים — כולם לא שוברים את הלוח).
- **ספק לוח זמנים/בפועל:** להחליף/להוסיף פונקציה ב-`SCHEDULE_PROVIDERS` (מחזירה `[{type, date, when, period, source, estimated}]`) או להחליף את `fred_actual` / `fred_latest` (אותן חתימות). שאר המערכת, ה-API וה-UI לא משתנים.
- **אירוע חדש:** רשומה חדשה ב-`CATALOG` (שם, impact, שעה, הסבר, affects, ה-series ב-FRED אם יש, רגקס לכותרת בפיד הצפי).
- **אירועים תאגידיים (עתיד):** ספק נוסף שמחזיר את אותו מבנה (`type` חדש + `what`/`affects`) — ה-UI כבר מקבץ לפי תאריך.

### מגבלות ועלויות ⚠️
- **עלות: $0, בלי הרשמה לשום שירות.** ספק צפי מורשה (אם יחובר) = עלות חדשה שטרם נבחרה.
- **אין צפי כרגע (v11.1):** זו מגבלה מכוונת ולא באג — הוסר הספק הלא-מורשה. הלוח עדיין מציג מתי, מה פורסם בפועל, מה הקודם, ומה מושפע.
- **שמות כותרות של ספק צפי עתידי** יצטרכו התאמה ל-`CATALOG[...]["match"]` (הרגקסים הקיימים הם נקודת פתיחה בלבד ולא נבדקו מול ספק חי); אירוע שלא מופה יופיע (תאריך מ-FRED/כלל) אבל בלי צפי.
- **ISM / Conference Board / מישיגן:** אין לוח רשמי חינמי — תאריכים מוערכים בכללים (ISM: יום עסקים 1 ו-3; CB: יום שלישי אחרון; מישיגן: שישי 2 ושישי 4) ומסומנים "מועד משוער"; ואין מקור חינמי רשמי לנתון בפועל. claims: כל חמישי 08:30 (רביעי אם חמישי הוא חג).
- **FRED CSV ציבורי** אינו API מתועד — אם ייחסם/ישתנה, "בפועל" ייעלם (לוח הזמנים והקודם ימשיכו). חלופה: מפתח FRED חינמי (`api.stlouisfed.org`) — דורש הרשמה.
- **פרסר העמוד של Census** תלוי במבנה ה-HTML; בכשל — מכירות קמעונאיות נלקחות מהגיבוי ב-DB (אם נשמרו).
- **דחיות פרסום** (כמו בשביתה הממשלתית) משתקפות אוטומטית כי הקבצים הרשמיים מתעדכנים; גיבוי ה-DB משמש רק כשמקור נופל.
- **FOMC 2027** טנטטיבי; הטבלה הקבועה דורשת עדכון שנתי. **FRED:** נתון בפועל מופיע דקות עד שעה אחרי הפרסום.
- **Render Free** נרדם — הקריאה הראשונה אחרי שינה איטית (קאש בזיכרון נמחק; ה-DB מחזיר את הצפי השמור).
- **נבדק רק על נתוני דמה** (ראה סעיף 15).
